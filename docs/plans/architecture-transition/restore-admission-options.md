# A2.4.2b — выбор политики после восстановления журнала

Дата: 2026-10-13. A2.4.2a завершён. Этот документ — подготовленное архитектурное
решение; ни один выход из inspection ещё не реализован. Рабочие config/runtime
не менялись. Установленный schema-6 worker продолжает обслуживать проверки.

## Почему требуется решение

После restore старой SQLite может отсутствовать запись об уже выполненной
команде и её idempotency key. Новый epoch или пустая restored queue этого не
исправляют. Нельзя просто снять marker и принимать прежние запросы.
При этом неизвестные прежние процессы могут владеть workspace или внешним
ресурсом. Изменение journal incarnation не останавливает их.

Оба варианта требуют проверяемой остановки/изоляции прежних owners и явного
отделения новых запросов от retries утраченных операций. При недостатке
свидетельств admission остаётся закрытым; исторические Running/Ready не служат
доказательством. Lost records нельзя обнаружить только по восстановленной БД:
проверка всех перечисленных в ней Job Objects не доказывает отсутствие
неперечисленных процессов. Нужны сведения действующего owner вне restored
snapshot либо явно проверенный переход к чистому окружению.

## Варианты

| Решение | Пользовательский результат | Цена и ограничения |
| --- | --- | --- |
| Новая пара controller/worker с новым instance ID и новым журналом — рекомендуется | Старый журнал остаётся отдельной read-only историей. Агентов явно подключают к новой паре и начинают новые запросы; прежние IPC/session endpoints не возобновляют admission. | Меньше изменений в обычном write path. После recovery нужно переподключение клиентов; объединённое представление текущей работы и архива появится в A3. Нужен отдельный проверяемый cutover физических owners, включая отсутствующих в backup. |
| Прежняя пара с независимым durable журналом admission/dedup | Клиенты могут сохранять pairing; запись о принятом key переживает restore основной БД. При утрате результата key остаётся блокированным/неопределённым. | Новый storage authority вне backup основного журнала, порядок записи между хранилищами, reconciliation и crash tests на каждом шаге. Легко ошибиться в атомарности; это существенно больше фундаментальных изменений. До первого появления ledger прежние lost keys не восстанавливаются автоматически. |

В обоих случаях exe остаются в `K:\_proj-26\winbridge\runtime`; новый instance
не означает новый путь программы и не требует генерации runtime directories.
Запреты read-only inspection сохраняются; операция смены пары/ledger выполняется
отдельной административной процедурой, не обычным restart worker.

## Последовательность после выбора

1. Зафиксировать typed restore/cutover states и evidence: исходный config/journal,
   scope пары, сведения физических owners, готовность клиентов и admission barrier.
   Отдельно проверить, какие доказательства нужны при lost records и legacy workers.
2. Реализовать offline preparation/preview в новом тестовом namespace. Сначала
   показать проверяемый план и точные paths; не менять установленный config и не
   предоставлять универсальную команду удаления marker.
3. Реализовать commit/cutover выбранной модели с отказом при stale identity,
   недостатке physical evidence и при попытке v1 retry перейти через новую границу.
   Перед разрешением эффектов проверить всю границу, включая connection routing;
   если instance separation недостаточно, потребуется новый fenced request contract.
4. Проверить lost ACK/key, старого клиента и callback, сбой между каждым durable
   шагом, частичный cutover, неизвестный процесс и restart. История не объявляется
   новым фактическим состоянием; прежняя операция не перезапускается автоматически.
5. Выполнить isolated Windows gate через прежний рабочий worker, используя
   проверенные caches без массового удаления. Только после полного A2.4/A2
   подготовить общий update worker/desktop и перейти к A3 read model/discovery.

## Ревью решения

Новая пара даёт границу клиентских retries, но не заменяет physical proof.
Новый ledger даёт surviving admission evidence, но не восстанавливает outcome
и сам должен переживать сбой/restore. Нельзя обещать «exactly once» произвольной
внешней команде или трактовать смену host/session как доказанную остановку.
Выбор влияет на persistent config identity, storage и будущие MCP contracts;
поэтому его следует согласовать до реализации A2.4.2b. Остальные этапы плана
остаются в прежнем порядке. Текущий marker и installed worker не меняются.
