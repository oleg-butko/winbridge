## Что завершено и исправлено

Final backup выполняется после подтверждённого завершения **точного** старого
worker и захвата его исходной instance lock, перед заменой runtime. Он включает
shutdown acceptance и последние callback writes. Используется SQLite backup API,
а не копирование открытых DB/WAL/shm. Создание destination — create-only; реальные
File ID/size/SHA, binding, PID/grant и cleanup проверяются до `Verified`.

Intent сохраняется до ACK и запуска helper; повтор запроса наблюдает ту же attempt.
Неизвестный исход — terminal `Indeterminate`, без запуска второй попытки.
Supervisor держит исходный `ShutdownExitGuard`, backup driver получает immutable
loan через Arc. Исторические `Exited`/`Verified` и JSON не восстанавливают живые
process handles/instance lock и не дают разрешения на новые эффекты.

Ревью и native-прогоны выявили и устранили следующие проблемы:

1. DB `Exited` фиксируется раньше retirement shutdown driver и публикации custody.
   Fixture теперь **до первого** backup mutation readonly-наблюдением ждёт idle,
   physical custody и root `Replacing`. Production admission не ослаблен.
2. После управляемого падения тестового Job первое readonly-чтение SQLite могло
   получить transient disk I/O. Fixture повторяет только тот же readonly snapshot
   для Storage/disk-I/O, до 5 секунд с интервалом 25 ms. `Corrupt` не повторяется;
   никаких helper/file effects это не переисполняет. В успешном финальном прогоне
   счётчики таких повторов равны нулю. Public snapshot сохраняется до kill.
3. Win32 rename с relative RootDirectory/leaf дал error87. Исправленный adapter
   использует абсолютный UTF-16 path, `RootDirectory=NULL`,
   `ReplaceIfExists=false` и удерживает no-delete handles всех ancestor directories.
   Collision test принимает именно error80/183. Второго OS attempt/fallback нет.
4. Local proof verifier сравнивал raw stderr с LF с очищенной Rust-причиной.
   Теперь повторяет удаление Unicode Cc и ограничение 900 scalar chars, сохраняя
   raw cleanup failure отдельно. Тот же готовый Windows proof перепроверен;
   повтор Windows не потребовался. Добавлены две Python-регрессии.
5. Прогресс actual Main теперь включает оба fault names и завершение каждого case,
   чтобы одинаковое `None` не скрывало переход между четырьмя полными сценариями.

Предыдущие неуспешные отчёты сохранены как failed. Ошибок установленного worker
не обнаружено; production runtime/config/journal не заменялись.

## Следующая реализация: U2.2, в строгой последовательности

1. **Immutable binding и подготовка ledger.** Связать в одной admission transaction
   saved root `Replacing`/revision, current owner/epoch/supervisor launch,
   config/directory IDs, baseline/preimages, candidate artifacts/health, shutdown
   и именно `Verified` final backup. Проверять причинные связи и fingerprints;
   не принимать независимые правдоподобные JSON как разрешение на замену.
2. **Durable preparation.** Четыре candidate copies и новый manifest создаются
   независимо в `runtime/update/<id>/prepared-runtime`, create-only. Перед каждым
   create/copy сохранить intent, после readback — actual ID/hash/size receipt.
   IDs будущих prepared files неизвестны до копирования: одного заранее заполненного
   `FileExchangeBatch` недостаточно, нужна preparation phase. Candidate не расходовать
   move. Добавить migration/read snapshot/old-reader refusal и negative tests.
3. **Fresh permission и consuming custody handoff.** Только после checked backup,
   admission и отсутствия loans атомарно забрать исходный guard из `Custody`
   (`Arc::try_unwrap`; при busy вернуть custody на место). Сохранить pinned exited
   process, original locked worker state/instance lock и directory pins в новом
   replacement guard. Освободить old-set read pins только внутри этого handoff.
   Не drop/reacquire guard, не собирать его из DB. Immutable loan нельзя превратить
   в право rename. Новый guard сверяет разрешённый per-file progress вместо
   требования «весь старый runtime неизменен» после первой законной замены.
4. **Consuming file driver.** Retire intent → owned old-file move в отдельный
   retained directory → receipt; place intent → prepared-file move → receipt.
   Fixed roles, same-volume, no-overwrite, manifest последним. Все необходимые
   rename handles получить/сверить до первого move. Unknown outcome сохраняет
   prefix и ведёт к ManualIntervention, без replay/автоматического restore.
5. **Versioned actor и фактические fault tests.** Новый internal contract/view,
   responsive mailbox, ACK после commit, duplicate observation без dispatch.
   Только atomic final manifest receipt может выдать trusted `FilesVerified`.
   Actual Main→shutdown→backup→replacement gate: locked file, collision, disk full,
   changed parent/scope/mixed set, crash после каждого intent/receipt, startup
   refusal в partial set, сохранение displaced originals и отсутствие перезапуска.
6. **Отдельно activation.** Guarded новый worker, передача instance lock,
   effect-free verification/local health и exact controller confirmation;
   затем agent-visible management contract/status/policy. U3 desktop/migration/
   rollback и U4 bootstrap остаются обязательными до public install.

Первая вертикаль следующего агента — пункты 1–2, без изменения рабочего runtime.
После code review и локальных tests — отдельный изолированный native gate;
уже пройденные U2.1/SDK gates не повторять без новой причины.

Важные ловушки:

- Не добавлять новые persisted tables скрытно под schema13. Если нужна schema14,
  обновить compiled-current helper checks и подобрать **совместимые** old-role/
  candidate archives. Старый compiled13 exporter не обязан понимать будущую БД.
  Сохранить actual12/13 references как immutable fixtures.
- В старом обзорном плане `file_intents/file_receipts` перечислены концептуально;
  готового общего replacement ledger в коде нет. Проверять реальные schema tables.
- Синтетические health/backup fixtures местами имеют неполный граф. Для joined
  admission сделать согласованный fixture builder, не ослаблять validator ради теста.
- Внутренне tagged unit variants Serde могут проигнорировать unknown fields;
  в новой FSM использованы empty struct variants. Для новых контрактов проверять
  строгий ingress; frozen старым версиям не назначать новый смысл.
- Смена manifest не делает комплект из пяти файлов атомарным. Целостность дают
  maintenance barrier, startup refusal, per-file journal и manifest-last.
