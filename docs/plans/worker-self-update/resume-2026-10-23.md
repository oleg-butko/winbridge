Текущие версии: **updater journal14 / worker journal16 / supervisor v16 / view8**.
Frozen v1–15 сохраняют прежнюю семантику; старые views не получают поле
`runtimePreparation`. Успешные прежние gates schema13 не являются проверкой14.
**Самообновление целиком не готово. Public install/CLI/MCP capability отключены.**

Preparation создаёт четыре независимые копии candidate binaries и новый manifest
в `runtime/update/<update-id>/prepared-runtime`. Original runtime, candidate payload,
previous-runtime copies и worker journal остаются прежними. Directory/file intent
сохраняется до IO, receipt — после File ID/bytes/SHA readback, manifest последним.
Полный успешный путь имеет revisions0→12. Admission связывает baseline, preimages,
artifacts, health, shutdown, Verified backup, config/root/owner/epoch/launch.

Fresh non-Serde permit выдаётся однократно после commit. Дубликат наблюдает тот же
attempt. Driver заимствует **оригинальный** `ShutdownExitGuard`; custody остаётся
у supervisor. Saved Prepared/Exited/Verified — история, а не kernel handles или
право повторить эффект. После crash custody=false; неизвестный исход не повторять.

## Следующий вертикальный блок: actual preparation faults

Это план следующей реализации, **не уже существующие flags/hooks/tests**.
Synthetic IO tests уже закрывают occupied destination, failed directory/file
receipt и stream fence после64KiB. Теперь нужны те же гарантии под actual supervisor
admission/custody и настоящим owned crash, до подключения rename.

1. **Занятый prepared-runtime.** После Verified backup создать sentinel в собственном
   test destination, затем PrepareRuntimeFiles. Проверить отказ без overwrite,
   exact сохранённый prefix/Indeterminate, тот же attempt при duplicate, отсутствие
   повторного create и сохранность old runtime/candidate/DB/backup.
2. **Изменённый candidate.** После завершения health/backup, перед preparation,
   изменить один файл только собственного isolated payload. Driver должен обнаружить
   несовпадение source pin/hash до копирования; сохранить ошибку без нового эффекта.
   Намеренно изменённый файл тоже не восстанавливать автоматически.
3. **Crash после IO до receipt.** Нужна детерминированная feature-only test barrier
   на заданном directory/file prefix, marker с actual attempt/revision/PID/File ID
   и bounded wait. Завершить только собственный тестовый Job. Cold view сохраняет
   issued history/partial files, custody=false и не выдаёт permit/replay.
   Не заменять barrier гонкой «увидеть Issued и успеть убить процесс».

Test hook должен быть строго `update-validation`, scoped к isolated update/owner/
epoch/attempt, без произвольных путей и без изменения public v16 semantics.
Обычная production-сборка не должна читать hook/env. Для updater hook потребуется
явно собрать и выбрать **тестовый** validation updater в old roles: существующий
setup специально берёт feature-enabled worker, остальные роли — normal old stage.
После выбора считать actual descriptors/hashes и сформировать соответствующий
known manifest. Не подменять feature-enabled binary после создания manifest и
никогда не устанавливать его в рабочий runtime.

Расширить native PS/Python runner и verifier отдельным fault режимом, сохранить
happy gate. Для каждого case связать exact source/target, scope, retained graph,
file identities, prefix, duplicate и post-crash observation; отрицательные mutations
должны отвергать ложные passed flags и пропущенные связи. При первом post-Job read
использовать существующий `observe_after_owned_exit`: bounded повтор **readonly**
snapshot лишь при transient Storage/disk I/O; Corrupt не ретраить. Это не разрешение
повторить файловый эффект. Не удалять failed Windows evidence.

## Дальнейшая последовательность после fault gate

1. **Consuming replacement custody.** Fresh admission и отсутствие loans; забрать
   исходный guard через проверенный consuming handoff (`Arc::try_unwrap`, busy
   возвращает custody). Сохранить original exited process/state/instance lock и
   directory pins. Old-set read pins отпускать только внутри handoff; не делать
   drop/reacquire и не реконструировать custody из journal/JSON.
2. **Durable rename ledger и driver.** Immutable preparation/backup binding;
   retire intent → exact old-file no-overwrite move → receipt → place intent →
   prepared-file move → receipt. Все пять files, manifest последний. Реальный
   Windows adapter использует absolute UTF-16 destination/NULL RootDirectory и
   pinned ancestors. Один OS attempt, без overwrite/copy-delete fallback.
3. **Trusted FilesVerified и native replacement faults.** Atomic full-set receipt
   перед root transition; mixed set/startup refusal, collision/locked exe/diskfull,
   crash на intents/receipts, same duplicate без новых effects. Raw API не может
   заявить успех вместо trusted driver. Unknown outcome → manual intervention.
4. **Activation.** Новый worker verification mode, instance lock/ownership handoff,
   exact local health и controller-pinned confirmation. Открытие scheduler/effects
   только после согласованных guards. Candidate-updater compatibility должна быть
   проверена ещё до production drain, как указано выше.
5. **Public management и U3.** Opt-in local policy, versioned CLI/MCP/status;
   desktop save/ACK/exact exit, background tray без main/popup flash, уведомления,
   actual consistent migration rehearsal, old-reader refusal и rollback boundaries.
6. **U4.** Когда isolated pipeline готов, остановиться для одного согласованного
   ручного bootstrap установленного worker/desktop/updater. Затем проверить настоящее
   автоматическое обновление стабильного runtime без Ctrl+C/ручной распаковки.
   Только после U4 updater считать завершённым и вернуться к installed A4.3 gate.
