## Что реализовано и почему это устроено так

Финальный backup создаётся **после** exact exit прежнего worker и получения его
исходной instance lock, **до** первой замены runtime. Поэтому он содержит shutdown
acceptance и последние callback writes. Предварительный rehearsal и executable
preimages не заменяют эту копию. SQLite копируется через backup API; открытые
DB/WAL/shm нельзя копировать обычным файловым копированием.

Текущие контракты: updater journal **13**, worker journal **16**, supervisor
**v15**, view **7**. Старые v1–14 не получили нового смысла. Новая остановка
`ShutdownCandidateForBackup` проверяет marker экспортера старого worker ещё до
admission. `BackupWorkerState` сохраняет новую попытку до ACK и отправляет один
driver; `ObserveStateBackup` читает её состояние. Повтор не запускает второй helper.

Backup FSM: Prepared → Issued → ResumeGranted → Running → Cleaned → Verified.
Ошибка/неизвестный исход дают terminal Indeterminate без автоматического replay.
Каждый переход хранится с CAS и append-only history. Сохранённый JSON/Exited/
Verified — данные, **не** полномочия запускать процесс или заменять файлы.

Supervisor удерживает тот же физический `ShutdownExitGuard` через Arc; blocking
driver получает immutable loan. Mutex не удерживается на IO, mailbox отвечает на
status. При потере supervisor driver сохраняет loan до cleanup; новый процесс не
восстанавливает custody из журнала. Исторический backup показывается отдельно от
текущего OS владения. Raw lifecycle по-прежнему не может объявить FilesVerified,
LocalHealthVerified или ControllerConfirmed: для этого нужны будущие drivers.

Старый worker имеет ранний CLI `--export-update-state INPUT SHA`. Он открывает
Store readonly своей schema, без обычного Worker/recovery/scheduler/controller,
и сверяет input/PID/grant, живой supervisor, config, directory/file identities,
source authority и shutdown receipt. Destination create-only. Driver проверяет
cleanup и реальные SHA/size/File ID копии до записи Verified. Partial файл
сохраняется, не перезаписывается и не получает статус готового.

## Первый шаг после разрешения продолжить: закончить U2.1 fault gate

Scaffold уже в Git под `update-validation`, обычный runtime его не включает:

1. `BackupFault::ExistingDestination` создаёт sentinel по fixed destination;
   ожидается отказ без перезаписи sentinel, Indeterminate и пустой owned Job.
2. `ExitAfterCopy` завершает helper с79 после создания проверенной копии;
   ожидается Indeterminate, сохранённый файл, cleanup и отсутствие retry.
3. `WrongInputReport` искажает input SHA отчёта;
   ожидается отказ binding, cleanup, сохранённая копия и отсутствие retry.
4. `HoldBeforeCopy` публикует local marker с actual PID/attempt и ждёт release;
   parent должен завершить только свой validation Job и доказать сохранение
   Running history без новой custody/повторного helper после crash.

Parent fixture принимает `backupFaults` (default false), выбирает четыре случая
с метками `None-ExistingDestination`, `None-ExitAfterCopy`,
`None-WrongInputReport`, `None-HoldBeforeCopy`. Partial parent assertions добавлены,
но ещё не исполнялись. В том числе нужно проверить, что feature-only input/SHA
действительно наследуются helper через существующий supervisor launch.

**Ещё отсутствуют** PS switch/selection/whitelist, Python CLI mode и строгий
fault-proof verifier. Happy `--final-state-backup-gate` их сейчас не запускает.
Не считать наличие enum подтверждением покрытия.

Рекомендуемый порядок:

1. Review scaffold и дописать режим `-FinalStateBackupFaults` / Python
   `--final-state-backup-faults` как mutually exclusive mode. Он должен включать
   Main+final backup, передавать `backupFaults=true`, ожидать ровно четыре случая
   и отдельный kind `state_backup_faults_native_proof`.
2. Расширить только explicit whitelist логов нужными четырьмя метками. Private
   supervisor client остаётся в локальном `supervisor-control.private`; никаких
   его bytes/token в shared proof/logs/Git/backup. Не вводить public bypass.
3. Verifier проверяет actual source/target, обычный stop proof, terminal error/
   cleanup/повтор, sentinel либо rows копии и after-crash history без custody.
   `HoldBeforeCopy` должен остаться Running, а не выдуманным Indeterminate/Verified;
   это **saved record**, при этом readonly projection после потери custody может
   показывать неопределённость. Сверить с текущей моделью view, не ослаблять её.
4. После локальных проверок закоммитить clean producer, собрать UI и экспортировать
   новый ZIP. ZIP `8bd7629` не содержит новых fault hooks. Target `31fa634` можно
   переиспользовать: updater13/worker16. Старый targetA294/schema12 не подходит для
   нового candidate health; сохранить его лишь как reference migration.
5. Объявить Windows run пользователю, проверить healthy/idle worker и ≥6GiB, затем
   выполнить **новый fault mode**, переиспользуя cache ниже. Не повторять всё U1.
   Новые flags ещё предстоит реализовать; готовой команды fault run сейчас нет.
6. При неожиданном installed worker остановить зависящие Windows действия. При
   обычной ошибке isolated fixture исправление и повтор ранее разрешены пользователем.
   Не выдавать вторую попытку внешней команды при неизвестном её исходе.
7. Проверить terminal task, все ready SHA/bytes, proof дважды и отрицательные
   мутации. Зафиксировать gate report. Только затем закрыть U2.1 в roadmap.

## Что делать после U2.1

U2.2 сначала спроектировать и review consuming replacement driver: exact old-set
preimages, подтверждённый final backup, живой original exit guard, local policy,
durable per-file intent → same-volume no-clobber replacement → SHA/File ID receipt.
Смешанный комплект не должен запускаться даже вручную; crash между любыми двумя
эффектами не должен выдавать ложный успех или автоматически повторять эффект.
Проверить locked exe, disk full/partial rename и crash after intent/receipt.

Затем activation: new worker в отдельном verification режиме до обычного dispatch,
точный config/schema/incarnation и controller-pinned handshake. Receipt/files сами
по себе не разрешают новые tasks. Подключить installation-level CLI/MCP/status и
opt-in local policy; обычная task внутри Job не должна владеть своим updater.

U3 — desktop save-before-exit, visible/tray/absent сценарии, один tray и отсутствие
вспышки окна, понятные notifications/звуки/ошибки, сохранение drafts и config,
migration rehearsal и rollback только до нового owner/effects с проверенными
preimages. Нельзя просто восстановить старую SQLite после новых effects.

U4 — один согласованный ручной bootstrap полной capability, затем настоящий
автоматический update из fixed runtime с отчётом и инструкцией восстановления.
Только после этого updater готов пользователю и можно возвращаться к A4.3.
