# WinBridge: краткое руководство v1

Актуально на 2026-10-10. Основные этапы разработки 0–7 завершены.

[WinBridge проверяет собственные изменения на Windows](winbridge-v1/README.md): постоянные `src`/`runtime`, обновление через Git и MCP, уведомления и ручной тест.

## 1. Что уже можно делать

WinBridge позволяет агенту в Debian выполнять работу на Windows. **Worker** исполняет команды и хранит историю, **controller** связывает его с агентом и подготавливает исходники, **desktop** показывает ход работы и предоставляет управление.

Готовые возможности:

- Выполнять **рецепты** — команды с фиксированными параметрами; при разрешении проекта — произвольные команды.
- Доставлять **конкретный Git commit** через shared: `/mnt/hgfs/shared/WinBridge` ↔ `K:\VMs\shared\WinBridge`. Проверять файлы по контрольным суммам SHA-256 и собирать из отдельной локальной копии. Поддерживаются доставка изменений и повторное использование проверенных блоков после обрыва.
- Выполнять **workflow**: «импорт → сборка → запуск → проверка готовности → подключение лога». Сохранять профили, получать файлы сборки с контрольными суммами, управлять приложением.
- Читать stdout/stderr, логи и историю; отменять дерево процессов; получать уведомления о проблемах.
- Настраивать проекты, рецепты и хранение вывода. Очистка старого stdout/stderr бывает ручной или явно включённой автоматической; история сохраняется.

Для агента нужны запущенные **worker и controller**. Крестик desktop скрывает окно в tray — значок возле часов Windows; «Завершить интерфейс» закрывает desktop. Принятая работа продолжается. Browser/dev UI — демонстрация; реальные команды доступны через native desktop, CLI и MCP.

Доставка незакоммиченных правок и очистка старых snapshots/cache пока не реализованы.

## 2. Как понимать интерфейс и результат

### Основные элементы

**Snapshot** — зафиксированный набор исходников с собственным ID.

| Элемент | Что показывает и зачем нужен |
| --- | --- |
| **Worker / Controller Debian** | Связь desktop с worker и worker с Debian; последнее подтверждение и ошибка соединения. |
| **Команда** | Проект, рецепт либо программа (Executable), аргументы как JSON-массив строк, относительная рабочая папка и timeout — предел времени. «Snapshot ID для сборки» выбирает проверенную копию; пустое поле использует корень проекта. |
| **Последние 10 задач / детали** | ID, статус, фактическая команда, источник рецепта, PID — номер процесса, события, stdout/stderr и exit code — код завершения. EncodedCommand показывается как читаемый PowerShell-сценарий. |
| **Доставка исходников** | Выбор опубликованного пакета, просмотр состава, импорт и его прогресс. «Готово для сборки» означает успешную проверку локальной копии; просмотр состава сам импорт не выполняет. |
| **Цикл разработки** | Профиль workflow, состояния его шагов, файлы сборки, запущенное приложение и лог. |
| **Внимание / История** | Проблемы, ссылки на операции, поиск и диагностика. «Прочитано» подтверждает уведомление; простое открытие этого не делает. |
| **Настройки / Tray и уведомления** | Проекты, рецепты, очистка вывода, звук и тихие часы. Сохранённый конфиг применяется после ручного перезапуска worker. |

Выбор проекта, восстановление полей или сохранение профиля **не запускают работу**. Нужна явная кнопка запуска.

### От запроса до результата

После запуска worker подтверждает **приём** и возвращает ID. Это ещё не результат. «Приём задачи не подтверждён» означает потерю ответа: задача могла быть принята. Предложенный повтор сверяет прежний запрос без второго запуска.

| Статус | Как его понимать |
| --- | --- |
| **В очереди** | Задача принята, ждёт свободного проекта; доступна отмена. |
| **Выполняется** | Появляются события и вывод; PID может появиться чуть позже статуса. |
| **Завершено** | Команда успешно закончилась. Для обычной команды это exit code 0. |
| **Ошибка** | Смотрите причину и вывод. Истечение timeout тоже даёт ошибку. |
| **Отменено** | Отмена завершена. Нажатие «Отменить» сначала лишь запрашивает остановку. |
| **Прервано** | Операция прервалась, например импорт при сбое; сама не возобновляется. |
| **Результат неизвестен** | Исход внешней команды после сбоя не установлен. Проверьте последствия перед новым запуском; автоматического повторения нет. |

Результат находится в деталях того же ID: **статус, причина/exit code, stdout/stderr и события**. stdout — обычный вывод; stderr — диагностика, которая не обязательно означает ошибку. Пустой stdout допустим. UI показывает хвост вывода; весь сохранённый вывод доступен страницами через CLI/MCP. Потери из-за квоты или очистки обозначаются явно.

**Потеря связи — отдельное состояние.** «Worker недоступен» или «Нет свежего соединения с controller Debian» означает отсутствие свежих данных. Задача от этого не становится ошибочной. После восстановления читается прежний ID. Ошибка записи журнала отдельно приостанавливает новые запуски.

В workflow шаги проходят состояния «Ожидает → Выполняется → Подтверждено»; при ошибке последующие шаги могут быть «Пропущено». Возможны также отмена и неизвестный исход. После успешного запуска workflow завершён, **а приложение может продолжать работать**. Его отдельные состояния: ожидается готовность, готово, остановка запрошена, остановлено, завершилось, ошибка или неизвестный исход. Для него используется «Остановить приложение».

## 3. Как подключить новый проект

Обычно достаточно настроек и команд проекта:

1. **Создать локальную папку Windows**, например `K:\WinBridge\workspaces\my-app`, вне shared и корней других проектов.
2. **«Настройки» → «Добавить проект»**: задать ID `my-app`, путь к созданной папке и разрешение произвольных команд. Рецепты сборки/запуска добавляются в JSON конфигурации; можно выбрать общий профиль рецептов.
3. **Сохранить конфиг и вручную перезапустить worker**, завершив нужные активные операции. Проверить появление проекта в списке.
4. **Для доставки добавить тот же ID в конфиг controller на Debian**: `sourceRoot` — Git-репозиторий, `sourceMode` — `commit`. Работающий MCP-адаптер после изменения конфига перезапустить. Для команд без доставки этот шаг не нужен.
5. **Создать workflow-профиль**: snapshot, сборка/запуск, признак готовности, лог и файлы сборки. Проверить запуск, вывод и остановку.

**Профиль рецептов** объединяет общие команды нескольких проектов; **профиль workflow** хранит параметры цикла. Обычно достаточно конфигурации и build script. Специальная проверка готовности может потребовать дополнительного обработчика.

Примеры: [worker config](../../examples/worker.config.json), [controller config](../../examples/controller.config.json), [общие рецепты](../guides/project-profiles.md), [подключение проекта подробно](../guides/project-integration.md).

## 4. Что агент получает через MCP

MCP предоставляет агенту **33 инструмента WinBridge**. Они используют тот же worker и журнал; действия агента видны в desktop.

| Возможность | Примеры инструментов |
| --- | --- |
| Узнать связь, версию, проекты и доступные функции | `winbridge_info`, `winbridge_controller_status` |
| Выполнить команду, прочитать результат/вывод, отменить | `winbridge_submit`, `winbridge_get_task`, `winbridge_read_output`, `winbridge_cancel` |
| Опубликовать, просмотреть и импортировать исходники | `winbridge_publish`, `winbridge_publish_delta`, `winbridge_publish_resumable`, `winbridge_import_snapshot` |
| Запустить и проверить полный цикл | `winbridge_submit_workflow`, `winbridge_get_workflow`, `winbridge_cancel_workflow` |
| Проверить приложение, прочитать лог, остановить | `winbridge_get_application`, `winbridge_read_application_log`, `winbridge_stop_application` |
| Запросить внимание и работать с уведомлениями | `winbridge_request_attention`, `winbridge_list_attention_events`, `winbridge_acknowledge_attention_event` |
| Найти историю, узнать объём журнала, подготовить диагностику | `winbridge_history`, `winbridge_storage_usage`, `winbridge_prepare_task_diagnostic` |

Сценарий агента: узнать возможности → отправить задачу → получить ID → читать состояние и вывод → сообщить результат. Перед workflow публикуются исходники; workflow сам выполняет импорт и остальные шаги. Публикация сама сборку не запускает.

Ключ запроса (`idempotencyKey`) позволяет получить прежнюю операцию при повторе тех же параметров. Закрытие MCP не отменяет работу. Настройка проектов и очистка вывода доступны локально через desktop.

MCP-клиент запускает адаптер в Debian; controller и Windows worker должны уже работать:

```bash
./target/debug/winbridge-controller --config .winbridge/controller-snapshot.local.json mcp
```

Настройка этого запуска в клиенте делает инструменты доступными агенту. [Полный контракт MCP](../guides/mcp.md).
