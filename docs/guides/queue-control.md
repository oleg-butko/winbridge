# Очередь и пауза — A4.2

Кандидат в разработке, 2026-10-16. Проверка на Windows и обновление установленного
worker ещё ожидаются. [План и инварианты](../plans/architecture-transition/queue-control.md).

WinBridge различает **приём запроса**, **начало запуска** и **завершение работы**.
Общий лимит работ A4.1 ограничивает исполнителей. Лимит очереди ограничивает число
принятых незавершённых корневых запросов, включая уже выполняемые.

После обновления worker можно явно добавить в корень его local config:

```json
"queuePolicy": {
  "maxPendingRoots": 100,
  "maxPendingRootsPerProject": 40
}
```

Это фрагмент, значения 1..10000; лимит на проект необязателен и не превышает общий.
Без раздела приём остаётся прежним. Изменение config требует обычного ручного
перезапуска worker. Рабочие лимиты автоматически не задаются. Если новый лимит
ниже уже принятой очереди, задачи сохраняются: новые запросы ждут освобождения
ёмкости у отправителя и пока не считаются принятыми.

Обычный task, import и workflow занимают по одному месту. Import/build/start
внутри workflow второго места не занимают. После завершённого startup приложение
может продолжать работать, уже не занимая root quota; его процессы и ресурсы
по-прежнему принадлежат worker. Неопределённое физическое завершение сохраняет
work slot A4.1 до проверки освобождения — лимит очереди этого не отменяет.

В desktop блок «Очередь запросов» показывает число запросов по проектам, лимиты,
режим, причины ограничения и ревизию. Две кнопки работают независимо:

- «Приостановить приём»: новые roots отклоняются до ACK. Уже принятые запросы
  продолжают проходить очередь; повтор их idempotency key возвращает прежний ID.
- «Приостановить запуск»: новые исполнители не получают claim. Уже начатые запуски
  продолжаются, результаты, output и отмена доступны. Приём может оставаться открыт.

Обе паузы сохраняются после restart. Закрытие desktop ничего не отменяет и не
возобновляет. Состояние меняется только после квитанции worker либо нового свежего
наблюдения; нажатие кнопки само по себе не подтверждает изменение.

До отправки desktop сохраняет command ID, journal scope и исходную revision.
При потере ACK команда остаётся видимой; повторное открытие окна её не отправляет.
«Проверить квитанцию» только читает результат. «Повторить исходную команду» передаёт
те же параметры и возвращает прежний receipt, если изменение уже выполнено.
При конфликте ревизии обновите состояние и примите новое явное решение. Старый
запрос не подстраивается автоматически под чужое изменение. Команда из другой
journal incarnation не переносится в новый журнал.

MCP `winbridge_info.info.contractCatalog.queueControl` содержит тот же readonly
срез: mode, pending roots, policy, revision, blockers и scope. Agent не получает
сетевую команду снятия пользовательской паузы. Local SID named pipe/Unix IPC
обслуживает отдельный контракт `winbridge.queue-control` v1. Уже разрешённые
произвольные команды остаются доверенным доступом пользователя; это разделение
интерфейсов, а не sandbox для недоверенных программ.

При отсутствии поддержки, потере свежей связи или read-only inspection управление
недоступно. Повторные ключи и receipts сохраняются. RPC 1/2 не меняется;
новая journal schema 13 содержит root index и состояние/квитанции паузы.
Migration 12→13 создаёт consistent SQLite backup; прежний worker schema 12
новую БД не открывает. До готового Windows gate рабочий journal не мигрируется.
