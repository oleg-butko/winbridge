# Диагностика восстановленного журнала

Эта возможность относится к candidate архитектуры A2.4.2a, schema 11.
Установленный рабочий worker пока использует schema 6; заменять его ради этой
инструкции не нужно. [Контракт и ограничения](../plans/architecture-transition/journal-inspection.md).

Режим нужен после восстановления старой базы или когда startup сообщил о
конфликте старых владельцев ресурсов. Старый журнал может не знать о недавно
запущенной команде; обычное повторение запроса тогда создаст второй эффект.

При остановленном совместимом worker используйте его существующий локальный
конфиг, например в PowerShell из каталога candidate runtime:

```powershell
.\winbridge-worker.exe --config .\winbridge-worker.local.json serve-recovery
```

Worker оставьте запущенным. Desktop можно открыть обычным способом; controller
и CLI также могут читать историю. Оранжевый блок «Диагностика восстановления ·
только чтение» объясняет ограничения. Доступны saved commands/output/results,
imports/workflows/applications и события внимания. «Выполняется» или «Готово»
в этом режиме описывает сохранённую запись, а не проверенное состояние процесса.
Запуск, отмена, остановка приложения, ACK, очистка output и изменение конфига
запрещены. Диагностика не запускает и не останавливает прежние процессы.

В `stateDirectory` создаётся `journal-recovery.required`. Он хранится отдельно от
SQLite: обычный restart с `serve` получает отказ даже после замены только базы.
Не удаляйте marker для возобновления. Безопасный выход с новой incarnation/парой
и разрешением неизвестных владельцев будет добавлен в A2.4.2b.

Схема должна совпасть с supported schema worker. При несовпадении база не
мигрируется, marker остаётся; используйте совместимую версию для диагностики.
Работающий worker нельзя запускать вторым процессом в том же stateDirectory.
В первом пакете требуется валидный config с существующими project roots; режим
не исправляет отсутствующие корни или повреждённую структуру самой базы.

Это ещё не автоматическое обнаружение отката. Перед любым восстановлением
базы необходимо отключить normal execution и сохранить блокировку. Остановите
все обращения к SQLite; копия открытого main file без WAL не является корректным
backup. Recovery mode не копирует, не заменяет и не ремонтирует базу за вас.
Процедуру восстановления и возобновления рабочего instance следует согласовать
отдельно; текущие automated tests меняют только собственные test journals.
