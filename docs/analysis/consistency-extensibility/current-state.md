# Текущее состояние: гарантии и ограничения

## Кто владеет состоянием

| Компонент | Что является его ответственностью | Чего он не подтверждает |
| --- | --- | --- |
| Debian controller | Связь с worker, корреляция RPC, публикация Git snapshot, вход для CLI/MCP | Отправка сообщения ещё не означает принятую Windows задачу. |
| Windows worker | Проверка допуска, долговечная очередь, journal, процессы, импорт, workflow, application, attention | Статус соединения не равен результату внешней команды. |
| Desktop | Представление данных worker, действия пользователя, tray/popup/звук | Открытое окно не владеет жизненным циклом задачи. |
| MCP adapter | Преобразование вызова агента в существующие controller/worker handlers | Выход агента не отменяет задачу, уже принятую worker. |

На Windows используется один экземпляр worker для instance/state с блокировкой
владения. Controller рассчитан на одну активную worker-сессию пары. Это не мешает
нескольким агентам: у каждого может быть собственный stdio MCP adapter,
соединённый с тем же controller.

## Консистентность принятия и результата

1. Worker проверяет запрос, разрешённый проект и команду, фиксирует её параметры.
2. Записывает `queued` в SQLite транзакцией и только затем возвращает принятую задачу.
3. Перед созданием процесса сохраняет намерение запуска. Текущий статус уже
   `running`, хотя PID в этот момент может ещё отсутствовать.
4. Результат и соответствующее событие attention фиксируются одной транзакцией.
   Сохранение output chunk и его метаданных тоже атомарно.

Journal использует WAL, `synchronous=FULL`, foreign keys. Один `Mutex<Store>`
сериализует доступ к одной SQLite connection. Поэтому два обработчика не могут
одновременно провести разные изменения через этот Store; уникальные ограничения
в БД дополнительно защищают ключи принятия.

Для tasks ключ уникален по `(project, idempotencyKey)`; imports и workflows имеют
свои аналогичные таблицы. Повтор с тем же содержимым возвращает существующую
операцию. Изменённое содержимое с тем же ключом отвергается. `requestId` исключён
из сравнения: он может измениться при восстановлении ответа. Ключ не является
общей идентичностью всего многошагового тестового прогона.

Это обеспечивает достоверное принятие и защиту от повторного запуска из-за
потерянного ACK. **Общей транзакции между SQLite и ОС нет.** Если worker падает
после сохранения намерения запуска, journal не доказывает, был ли процесс создан
и что он успел сделать. Recovery переводит такую задачу в `indeterminate`,
без автоматического повтора команды. Не запущенная `queued` задача сохраняется
в очереди; её дальнейшее исполнение проверяется заново.

Если итог процесса не удалось зафиксировать и восстановить в journal, worker
приостанавливает новые запуски и не выдаёт несохранённый итог за достоверный.
Это сознательный выбор консистентности: при проблеме единственного journal
доступность новых запусков уступает восстановлению учёта.

Источник: [Store: accept, finish, recover, append_output](../../../apps/worker/src/store.rs),
[допуск и journal fault gate](../../../apps/worker/src/lib.rs),

## Очередь и параллельное исполнение уже есть

`Worker::schedule` вызывается с интервалом 25 ms. `active_projects` хранит
владельца активной операции проекта. Task/import не запускается, если проект
занят; выполняющийся workflow также резервирует проект для своих дочерних шагов.
Конфигурация пока принимает только `maxConcurrentMutations = 1`.

Разные project IDs не делят эту блокировку: три проекта могут иметь три активных
процесса одновременно. `active_jobs` считает фоновые операции для жизненного
цикла worker, **но не ограничивает их количество**. Одного глобального лимита
процессов/сборок/нагрузки сейчас нет.

Порядок частично определяется порядком записей и временем принятия tasks/imports;
workflow обрабатываются отдельным проходом. Это не единая формальная FIFO очередь
всех типов операций и не алгоритм справедливого распределения между проектами.
Для обычных tasks нет общего лимита очереди при submit; для workflow есть предел
128 активных записей. Ограничения числа RPC не заменяют ограничение backlog.

Есть и ограничение роста истории: scheduler каждый тик вызывает `store.all()`,
читает и десериализует **все** task records, включая завершённые. Это выполняется
под journal/project locks. С увеличением истории и числа клиентов стоимость
этой работы будет расти; её нужно измерить и заменить выборкой активных записей,
прежде чем объявлять высокую производительность при многопроектной нагрузке.

## Несколько MCP клиентов и три разных тайм-аута

Controller обслуживает несколько локальных IPC клиентов. Через WebSocket
допускается до 16 RPC одновременно; обработчики worker могут работать независимо.
Каждый отдельный stdio MCP adapter обрабатывает сообщения последовательно.
Следовательно, несколько adapters дают одновременный вход от разных агентов;
один adapter не является глобальной блокировкой всех клиентов.

Нужно различать:

- **RPC timeout**: клиент не получил ответ за время обмена. Handler мог продолжить
  работу и принять задачу; исход принятия тогда неизвестен, новый ключ опасен.
- **Ожидание в очереди**: задача принята, но проект занят. Отдельного общего
  queue deadline сейчас нет; у startup workflow время ожидания учитывается
  в его сроке от `acceptedAtMs`.
- **Execution timeout**: worker завершает управляемое дерево запущенной команды.

Если worker недоступен, controller сейчас не создаёт долговечную offline очередь
исполнения. Принятая worker задача и ещё не доставленный запрос — разные состояния.
Controller connection/heartbeat сообщает свежесть связи, а не остановку процесса.

## Где состояние уже общее, а где ещё расходится по представлениям

**Общая история уже реализована:** `history` объединяет tasks, imports, workflows
и applications, фильтрует их по проекту/типу/статусу и использует cursor pagination.
Есть диагностика, сведения о хранении и долговечные attention events. Делать
вторую независимую историю для scheduler не нужно.

Однако history — список операций, а не согласованный снимок всей текущей работы.
Отдельные запросы task/workflow/application могут наблюдать разные моменты.
`observedAtMs` отмечает время ответа, но не является общей revision состояния.
Нет одного запроса, который одновременно объясняет очередь, ресурсы, связанные
шаги прогона и здоровье модулей. В journal есть записи и локальные события,
но нет общего event log, из которого уже можно восстановить всё состояние:
текущая система не является полным event sourcing.

Workflow связывает дочерние операции и закрепляет recipe pins. Создание дочерней
операции и запись ссылки родителя не всегда одна транзакция; определяемые из
workflow/step ключи позволяют восстановить связь без повторного запуска.
Нельзя считать весь workflow одним атомарным изменением или одной транзакцией.

После readiness стартовый workflow может быть успешным, а application продолжать
работать и позже завершиться с ошибкой. Это разные факты. Освобождение project
mutation slot после readiness не означает, что приложение перестало использовать
свои файлы, IPC или порт. Новый startup workflow ограничен live application,
но обычная direct command не получает автоматически отдельную защиту всех таких
ресурсов.

Источник: [history](../../../apps/worker/src/history.rs),
[workflows и applications](../../../apps/worker/src/workflows.rs),
[attention](../../../apps/worker/src/attention.rs).

## Расширяемость: фактические границы

Новый проект обычно подключается конфигурацией и recipes/profiles. Debian source
registry и Windows execution registry различаются по назначению; project ID
должен согласовывать их, а пути отличаются между ОС. Настройки worker сохраняются
с ручным перезапуском; принятые команды и workflow pins не должны менять смысл
из-за редактирования конфигурации.

Rust DTO находятся в `crates/protocol`, policy — в `crates/core`, но большая часть
долговечного orchestration сейчас находится непосредственно в worker. Startup
workflow фиксирован: import → build → start → readiness → log. Добавление общего
test-only pipeline потребует больше, чем новой recipe: общих состояний шагов,
результата тестов и правил доступа к workspace.

MCP schemas выводятся из protocol requests, что снижает риск расхождения полей.
При этом описания инструментов, разрешение удалённого вызова, handlers, capabilities
и UI распределены по нескольким местам. Новая DTO ещё не гарантирует поддержку
старым worker. Business errors в основном передаются строкой, без общего набора
кодов для автоматического решения «ждать / исправить запрос / сверить принятие».

Текущая доверенная локальная модель не идентифицирует каждого агента как отдельного
пользователя с ACL. Несколько проектов поддерживаются; изоляция недоверенных
клиентов и квоты по достоверной личности клиента — отдельная будущая задача.

## Проверки в этой сессии

Выполнен изолированный сценарий на Linux: собственный controller на loopback,
собственный worker, три проекта и три независимых MCP adapters. Рабочий Windows
runtime и его настройки не менялись.

| Наблюдение через настоящий MCP → controller → worker | Результат |
| --- | --- |
| По одной задаче в проектах A, B, C | Все три одновременно `running`, с разными PID. |
| Вторая задача A, пока первая A выполняется | `queued`, процесс ещё не создан. |
| Повтор исходного запроса A с тем же ключом | Тот же task/process; лишний запуск отсутствует. |
| Закрытие MCP adapter проекта B | B продолжает работать с прежним PID, статус читается другим клиентом. |
| Отмена первой A | Первая A `cancelled`, вторая A выполняется; B и C продолжают работу. |
| Завершение и уборка теста | В очереди/исполнении 0 tasks; количество созданных процессов A/B/C — 2/1/1. |

Локальный receipt, не включённый в Git:
`.winbridge/research/consistency-extensibility/three-clients-20261012T070120-c9cc3e/proof.json`.
Для MCP вызовов использован `Client` из
[scripts/validate-mcp.py](../../../scripts/validate-mcp.py); fixture-команды и
каталоги были временными. Это проверка механизма, не benchmark и не Windows gate.

Также прошли **19 tests**: `attention` — 10, `profiles` — 1, `runtime` — 8.
Они покрывают lost ACK/dedup, crash recovery, rollback attention, отказ journal,
профили проектов, отмену/timeout, output flood и path policy.

```bash
PATH=/home/user1/.local/bin:$PATH cargo test -p winbridge-worker \
  --test runtime --test profiles --test attention --locked --offline \
  -- --test-threads=1
```

Эти результаты не подтверждают ещё не реализованные fairness, global capacity,
очередь при offline worker или отзывчивость Windows UI под длительной нагрузкой.
