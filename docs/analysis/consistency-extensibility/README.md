# Консистентность и расширяемость WinBridge

Дата анализа: **2026-10-12**. Проверен исходный код commit
`a42cd7e5b90c40d4f789e2d5230668f0c9d810db`.
Это анализ и предложение развития; новые scheduler/API/UI здесь не реализованы.

## Основной вывод

Основа WinBridge подходит для нескольких агентов и 2–3 проектов: Windows worker
уже хранит очередь в SQLite, владеет процессами, предотвращает повторное исполнение
одного принятого запроса и допускает одновременную работу разных проектов.
Переписывать транспорт, доставку snapshot и владение процессами для этого не нужно.

Нужно расширить **управление этой очередью и представление состояния**.
Сейчас нет общего лимита нагрузки, формальной справедливости между проектами,
единых причин ожидания и согласованного обзора активных прогонов. Внутри одного
проекта ограничения, наоборот, слишком грубые для будущих независимых тестовых
workspace. Расширение workflow также требует правок его фиксированной структуры.

Рекомендация: оставить controller, worker и desktop отдельными процессами,
а внутри worker выделить небольшой общий планировщик, явные машины состояний
и запросы общего обзора. Сохранить SQLite источником истины.
Для текущего масштаба Kafka и отдельные микросервисы увеличат число мест,
между которыми придётся согласовывать состояние, без устранения этих ограничений.

Детали разделены на два документа:

- [Как устроено сейчас и что проверено](current-state.md).
- [Предлагаемый фундамент и сценарий трёх проектов](proposed-design.md).

## Что менять, а что сохранять

| Элемент | Решение | Зачем |
| --- | --- | --- |
| Windows worker как владелец исполнения | Сохранить | Клиент, UI и сеть могут исчезнуть без потери владения принятой задачей. |
| SQLite и commit до ACK | Сохранить | Это граница достоверного принятия; памяти или сообщения брокеру недостаточно. |
| Idempotency key, привязка к содержимому запроса | Сохранить | Повтор после потерянного ответа не создаёт второй процесс. |
| `indeterminate`, запрет автоматического повторения внешней команды | Сохранить | Запись в БД и создание процесса не составляют одну атомарную операцию. |
| Проверенные snapshot, отдельный Windows workspace, защита путей | Сохранить | Параллелизм не должен отменить достоверность исходников и границы проектов. |
| Логика допуска в `Worker::schedule` | Выделить и расширить | Нужны глобальные лимиты, ресурсы, справедливость и объяснение каждого ожидания. |
| Переходы задач/workflow/application | Свести к явным контрактам переходов | Добавление шага не должно требовать копирования recovery, cancel и journal-логики. |
| Чтение текущего состояния | Добавить общий согласованный обзор | UI и MCP должны получать одинаковые причины, связи и актуальность данных. |
| Фиксированный startup workflow | Позже расширить типизированными шагами | Нужны build-only, тестовые прогоны, результаты тестов и независимые workspace. |

## Очередь, state machine или Kafka

Это разные уровни. Очередь отвечает, что ждёт; планировщик — что можно начать;
машина состояний — какие переходы допустимы; журнал — что переживёт сбой;
общий обзор — что увидят пользователь и агент. Один из этих элементов не заменяет
остальные.

| Вариант | Что даёт | Цена для WinBridge | Оценка сейчас |
| --- | --- | --- | --- |
| SQLite + собственный небольшой scheduler + state machine | Долговечная очередь, правила запуска, общий статус в существующем worker | Миграции схемы, выделение переходов, тесты аварий и UI; без нового сервиса | **Рекомендуется** для одного Windows host. |
| Только Tokio channels / actor | Упорядоченное владение состоянием и ограниченный входной буфер | После сбоя память исчезает; долговечную очередь и recovery всё равно надо оставить | Полезный внутренний механизм, дополнение к SQLite. |
| Kafka | Распределённый журнал сообщений, независимые потребители, масштабирование потоков | Дополнительный broker, настройка и диагностика, согласование broker/SQLite/process; scheduler и UI остаются своей задачей | Рассматривать при нескольких машинах и независимых потребителях большого потока событий. |
| Durable workflow engine, например Temporal | Управление долгими workflow, история исполнения и доставка шагов workers | Новый сервис и эксплуатация, новая модель workflow, адаптация исполнителей, политик повторения и диагностики | Возможный будущий вариант при сложных межмашинных workflow; сейчас преждевременно. |
| Отдельные Rust микросервисы для sync/runner/attention | Независимые процессы и развёртывание компонентов | Сетевые ошибки, версии, транзакции между сервисами, сборка общего обзора и больше запущенных процессов | Статических Rust-модулей достаточно; выделять сервис только под конкретную потребность. |

Tokio предоставляет bounded channels для ограничения буфера и подход, в котором
одна задача владеет ресурсом, а другие отправляют ей сообщения. Наш вывод:
это подходит для организации worker, но сообщения в памяти не заменяют журнал.
[Документация Tokio](https://tokio.rs/tokio/tutorial/channels).

В SQLite WAL чтение может идти одновременно с записью, но писатель один;
WAL требует общего локального окружения и не предназначен для сетевой файловой
системы. Поэтому сохраняем БД на локальном Windows диске, а не в shared.
[Документация SQLite WAL](https://www.sqlite.org/wal.html).

Kafka описывает exactly-once для согласованных операций с Kafka topics;
внешние системы требуют дополнительного согласования. Наш вывод: Kafka не сделает
атомарными `commit` SQLite и Windows `CreateProcess` и не отменит
`indeterminate` у WinBridge.
[Модель доставки Kafka](https://kafka.apache.org/40/design/design/).

Temporal разделяет Workflow Tasks и Activity Tasks, хранит историю и доставляет
задачи через очереди; activity может иметь несколько попыток. Наш вывод:
при интеграции потребуется явно согласовать такую политику с запретом повторного
запуска команд неизвестного исхода в WinBridge.
[Модель задач Temporal](https://docs.temporal.io/tasks).

## Цена добавления возможностей

Ниже сравнительная сложность изменения WinBridge, а не оценка сложности тестов
самого проекта. «Небольшая» означает конфигурацию/локальную правку; «средняя» —
изменения нескольких компонентов с проверками; «большая» — изменение контракта
исполнения и восстановления. Абсолютные сроки без отдельного проектирования
не подтверждены.

| Изменение | Сейчас | После рекомендуемых расширений |
| --- | --- | --- |
| Новый проект с существующими recipe/profile и тестовым скриптом | Небольшая: Windows registry, Debian source registry, пути и проверка изоляции | Остаётся небольшой; UI обзора и scheduler автоматически учитывают project ID. |
| Ещё один read-only MCP инструмент над готовыми данными | Небольшая/средняя: DTO, handler, описание, схемы, проверки | Небольшая при общей модели чтения и явном каталоге операций. |
| Новый вид исполняемой операции | Средняя/большая: раздельные handlers, journal, cancel/recovery, capabilities, UI | Средняя: общий жизненный цикл и scheduler; новая предметная логика всё ещё нужна. |
| Тесты после сборки, без запуска приложения | Большая для полноценного общего API; сейчас можно выполнить скриптом как обычную задачу | Средняя: новые типизированные шаги и parser результатов, без нового queue engine. |
| Одновременные независимые прогоны одного проекта | Большая: одна project lease, общие каталоги/cache/IPC | Средняя после отдельных execution workspace и явных resource claims. |
| Несколько Windows machines | Большая: сейчас одна активная worker-сессия пары | Остаётся большой: routing, worker ID, местоположение snapshot, восстановление и ресурсы между машинами. |

Важное ограничение: общий scheduler уменьшает повторение инфраструктурного кода,
но не сможет сам определить, конфликтуют ли два теста Netwatch по IPC,
портам или изменяемым файлам. Это часть интеграции проекта и его ресурсной политики.

## Порядок развития и бюджет

Предварительные диапазоны — инженерные дни одного разработчика с тестами
и документацией; это ориентир масштаба, не измерение и не обещание срока.
Разбор Windows сбоев и сложных миграций может увеличить стоимость.

| Пакет | Результат | Ориентир |
| --- | --- | --- |
| 1. Допуск и очередь | Общий лимит, очередь проектов, причины ожидания, лимит размера очереди, выборка только активных записей | 4–8 дней. |
| 2. Общее чтение и управление | Согласованный обзор UI/MCP, revision, локальное изменение лимита/паузы, объяснения и уведомления | 4–8 дней; часть работы совместна с пакетом 1. |
| 3. Общие переходы и идентичность прогона | Постепенное выделение переходов, Run/Step связи, структурированные ошибки, совместимые миграции | 5–10 дней; выполнять по мере изменения затронутых handlers. |
| 4. Расширяемый тестовый pipeline | Build-only/test, execution workspace, test verdict и отчёты, resource claims шагов | 10–20 дней; отдельная функциональная задача. |

Для сценария 2–3 проектов сначала достаточно пакетов 1–2. Не нужно предварительно
переносить весь worker в actor, вводить DAG-язык или заменять journal на event sourcing.
Пакеты 3–4 устраняют следующие ограничения расширения и могут идти постепенно.
Диапазоны нельзя просто сложить: границы реализации пересекаются.

Новая Kafka/Temporal инфраструктура потребовала бы отдельного прототипа и оценки;
указанные сроки к такой миграции не относятся. Сейчас её цена сопровождения
не компенсируется потребностями одной пары Debian/Windows.

параллелизм, но не является Windows проверкой нового scheduler или нагрузочным
измерением. Подробные результаты и ссылки на код находятся в
