# Общие контракты и проверка обеих сторон

Часть [отчёта Actor Model + FSM](README.md), 2026-10-13.
Имена новых DTO/API ниже условные; это проектирование, не описание готовой функции.
Legacy v1 ниже означает нынешний API. Отдельного registry предметных контрактов
в нём пока нет; номера test-report/v1/v2 используются только для примеров.

## Четыре разные версии

| Версия | Что определяет | Когда изменять |
| --- | --- | --- |
| Transport envelope | Handshake, framing, correlation, RPC и доступные базовые сообщения. | Когда существующий envelope не позволяет выразить новую коммуникацию совместимо. |
| Business contract | Команды, payload, ответы, публичные FSM-переходы и смысл результата. | При новом поведении или несовместимом изменении прежнего поведения. |
| Persistence schema | Представление run/task/events и миграции SQLite. | При изменении хранения; это не обязано менять внешний контракт. |
| Build identity | Какая реализация каждого участника проверена. | Для привязки receipt к исполняемому коду; build number сам не заменяет контракт. |

Две разные сборки могут реализовывать один контракт. Один worker может одновременно
поддерживать v1 и v2. Внутренний enum может отличаться от wire enum, если
projection сохраняет обещания согласованного контракта.

Не следует использовать сериализацию всего внутреннего actor state как публичный
протокол: любое изменение реализации тогда заставит обновить каждый проект.
Нужны явные DTO на границе, например `test-report/v1` и `test-report/v2`,
и адаптеры к внутренней модели. Transport v1 не обязан становиться v2
при каждом новом предметном контракте.

Общий контракт не означает идентичную FSM во всех процессах. У caller есть
«ожидаю ACK / знаю accepted ID / связь потеряна», у worker — состояние исполнения.
После lost ACK caller ещё не знает о принятии, а worker уже может хранить queued.
Это допустимое расхождение знания: caller восстанавливает его по original key,
не меняет Windows state и не создаёт второй run.
Контракт описывает роли и допустимые наблюдения; SQLite worker остаётся
авторитетным источником исполнения, а не распределённой общей mutable памятью.

## Проверка текущей совместимости

В текущем коде PeerIdentity и SessionMessage используют строгие DTO,
Capability и TaskStatus — закрытые enum. Handshake проверяет равенство
`PROTOCOL_VERSION`, а список capabilities ограничен 16 элементами.
Добавление capability в новый binary может ломать handshake старого binary
ещё до выполнения проверок поддержки.

Источник:
[session DTO](../../../crates/protocol/src/session.rs),
[protocol DTO](../../../crates/protocol/src/lib.rs),
[controller handshake](../../../apps/controller/src/lib.rs),
[worker handshake](../../../apps/worker/src/network.rs).

В отдельном workspace был выполнен probe, использующий реальные DTO из
`crates/protocol`, без изменения основного Cargo manifest/lock:

| Вход для нынешнего reader | Фактический результат |
| --- | --- |
| Прежний Hello | Успешная десериализация. |
| Новая capability `actor_contracts` в Hello | Ошибка unknown variant. |
| Новое поле `supportedContracts` в PeerIdentity | Ошибка unknown field. |
| TaskStatus `starting` | Ошибка unknown variant. |
| Дополнительное поле `contractCatalog` в WorkerInfo | Успешная десериализация; поле игнорируется. |

Это пять assertions одного Linux probe, **не пять end-to-end тестов**.
Проверялась Rust-десериализация, без сети, TypeScript consumer и Windows runtime.
WorkerInfo не имеет `deny_unknown_fields`; такое поведение соответствует
[правилам Serde](https://serde.rs/container-attrs.html).

Локальные исследовательские файлы игнорируются Git:
`.winbridge/research/actor-fsm/probe/` и
`.winbridge/research/actor-fsm/proof.json`.
Повтор для сохранённого probe:

```bash
PATH=/home/user1/.local/bin:$PATH cargo run --offline \
  --manifest-path .winbridge/research/actor-fsm/probe/Cargo.toml
```

Этот результат задаёт направление миграции, но не доказывает, что старый
controller сохранит новое поле при forwarding, или что UI/MCP примет его.
Полный маршрут требует отдельных тестов.

## Совместимое обнаружение контрактов

Предлагаемый первый шаг — **сохранить прежний Hello и transport v1**.
Не добавлять неизвестные значения в его enum capabilities и новые поля
в строгий PeerIdentity. Добавить optional catalog к существующему WorkerInfo
и проверить обработку старым и новым controller/MCP/UI.

Новый caller сначала использует существующий Info. Нет каталога —
доступен только известный legacy набор; отсутствие каталога не означает
«сервер поддерживает всё». Старый промежуточный controller может отбросить
добавочное поле: это безопасная потеря обнаружения, а не повод пробовать
неизвестную команду.

Catalog содержит открытые строковые ID контрактов, точные версии, digest схемы
и признаки поддержки, проверки и включения. Строки здесь — метаданные расширения.
Payload конкретной исполняемой команды остаётся типизированным и проверяется
строго. Неизвестный contract ID не запускается.

Controller публикует доступность **всего маршрута**, а не просто список worker:
его собственный codec/forwarder, worker handler, нужный executor и профиль
должны поддерживать контракт. Пока новый controller не умеет маршрутизировать
команду, support одного Windows worker недостаточен.
Локальному desktop нужен свой результат обнаружения через local IPC.

Только после обнаружения известной поддержки на всех нужных участниках новый
caller использует условный `InvokeContract` или специализированный новый метод.
Его добавление в закрытый LocalRequest также требует обновлённого reader;
наличие каталога не отменяет этого требования.
Следует проверить generated JSON Schema/MCP и TypeScript вместе с Rust DTO.

Позднее transport v2 может иметь устойчивый discovery envelope с открытыми
metadata IDs и согласованием поддерживаемых версий. Это отдельная миграция:
у сегодняшнего handshake нет negotiation диапазона transport versions.
Удалять `deny_unknown_fields` повсюду ради расширяемости не требуется.

## Выбор версии и принятие запроса

Выбирается точная одобренная версия из пересечения поддержки участников
и разрешённого профиля. **Installed, supported, tested и enabled — разные факты.**
Профиль можно включать для одного проекта, сохраняя v1 у остальных.

В принятом run сохраняются как минимум:

- Contract ID/version и schema digest.
- Project, source commit/snapshot, profile/recipe и executor artifact.
- Consumer test pack и подходящий compatibility receipt.
- Original request, idempotency key и identity маршрута.

Перед commit provider повторно проверяет контракт и policy.
Catalog мог устареть между чтением и запросом: отказ должен означать
«не принято», без создания процесса. Поле `expectedRevision` уместно для
операций изменения policy; обычный request не должен требовать глобальную
revision всех независимых задач.

Версия **закрепляется на весь run**, включая связанные steps/reports.
После reconnect новая сессия может иметь другой каталог, но прежний run
не становится v1/v2 самопроизвольно. Capability loss — причина отказа нового
старта либо ограничения обслуживания прежнего run, а не подмена его результата.

| Ситуация | Допустимое поведение |
| --- | --- |
| Обе стороны знают только v1 | Работа по v1. |
| Caller новый, provider старый | Обычные действия по v1; новая функция явно unavailable. |
| Caller старый, provider новый | Provider сохраняет v1 DTO и семантику для этого caller. |
| Обе реализации поддерживают v2, совместный gate не пройден | Production остаётся v1; v2 разрешён только изолированной проверке. |
| Проверенная пара и профиль разрешают v2 | Новые запросы этого профиля принимаются по v2. |
| Новая сборка не соответствует receipt | Новые v2-запросы не включаются автоматически; повторная проверка изменённой части. |
| v2 уже принят, затем v2 выключен для новых запросов | Прежний run обслуживается по v2 совместимой реализацией. |

Общий глобальный атомарный switch двух компьютеров не нужен. Выбор до запроса,
проверка provider при admission и pin в принятом run дают определённое поведение
при гонке обновлений. Необходимо заранее определить границы действия receipt:
точные builds либо проверяемая эквивалентность конкретных неизменённых артефактов.
«Похожая версия» без доказательства не подходит.

**Contract gate и проверка нового application commit — разные процедуры.**
Изменение функциональности Netwatch при неизменном runner contract не требует
нового контракта WinBridge и обновления всех bridge binaries.
Source commit приложения является входом обычного run; его нужно записать
в результат, а не заранее объявить прошедшим compatibility gate.
Receipt прежде всего относится к реализациям протокола/adapter.

Чтобы это различие проверялось, выгодно отделить стабильный executor adapter
от изменяемого приложения под тестом. Если они находятся в одном binary,
новая сборка требует автоматической conformance проверки либо доказанного
неизменного contract adapter artifact. Первое включение кандидата проверяет
полный маршрут; последующие проверки используют явно определённые зависимости
и receipt scope. Это не должно превращаться в ручной Windows gate на каждый commit.

Особенно важно сохранить нынешнюю дедупликацию:
[Store::fingerprint](../../../apps/worker/src/store.rs) сравнивает сериализованный
TaskSubmission без request ID. Добавление default field не должно сделать
прежний payload другим при повторе того же key. Для v1 нужен совместимый
fingerprint; для нового контракта версия и значимые параметры входят в fingerprint.
После потерянного ACK повторяется исходный запрос или читается его статус.
Автоматическая попытка «то же самое, но другим методом/версией/key» запрещена.

## Что приносит сторона, запросившая расширение

Нужен versioned **contract pack**, сохранённый в Git или опубликованный как
проверяемый immutable artifact. Предлагаемая структура:

```text
contracts/test-report/v2/
  contract.json
  schemas/
  fixtures/
  consumer-tests/
  provider-tests/
  compatibility-cases/
```

`contract.json` описывает ID/version, purpose, roles, допустимые публичные
переходы, ошибки, ограничения, digest и команды тестового harness.
Fixtures задают запросы/ответы и условия проверки без фиксирования случайных PID,
timestamp и межпоточного порядка stdout/stderr.

Requester пишет consumer tests: реальный клиент строит запрос и читает ответы
через свой codec, проверяя нужное ему поведение. Provider затем проверяется
против этих ожиданий. Это соответствует consumer-driven contract testing:
ожидания потребителя становятся проверками поставщика.
[Pact: how it works](https://docs.pact.io/getting_started/how_pact_works).

Инициатор определяет потребность и примеры, но не единолично расширяет обещания
WinBridge. Стороны согласуют cancellation, failure semantics, лимиты и границы
полномочий. Provider добавляет tests своих invariants: path validation,
durable admission, dedup, recovery, несовместимость и ресурсы.
Ожидание requester «после timeout всё остановлено» нельзя принять, если это
только timeout ожидания RPC, а не подтверждение завершения дерева.

Для первого варианта достаточно собственного небольшого harness поверх
типизированных DTO и существующих approved Windows сценариев. Pact Broker,
его сервер и отдельная инфраструктура сейчас не обязательны.
Contract pack — набор проверяемых ожиданий и обозримых тестов, а не разрешение
автоматически выполнять любой присланный скрипт с правами пользователя.

## Уровни тестирования

| Уровень | Что обнаруживает | Что не доказывает |
| --- | --- | --- |
| FSM reducer: таблицы, properties, последовательности событий | Запрещённые переходы, terminal immutability, stale generation, гонки cancel/exit. | Реальную остановку процессов и надёжность disk I/O. |
| Codec/schema + golden fixtures | Чтение старых DTO, new/old schemas, Rust/TS/MCP соответствие. | Семантику исполнения Windows-команды. |
| Consumer/provider tests | Реализация действительно удовлетворяет ожиданиям конкретного клиента. | Полный reconnect/crash workflow лишь из независимых request/response примеров. |
| Store/effect fault tests | Commit-before-ACK, lost reply, сбои до/после spawn, восстановление без дубля. | Поведение Windows Job Object в Linux mock. |
| Native paired integration | Реальные Debian client/controller и Windows worker/executor, reports, cancel, reconnect. | Все возможные проекты и неподдерживаемые сочетания сборок. |
| UI/MCP parity | Один сохранённый факт одинаково виден агенту и человеку; stale/unknown не превращается в success. | Надёжность самого исполнителя без нижних уровней. |

Проверки неизменности terminal state не запрещают позднюю фиксацию отчёта
в независимой Report FSM. Нужно определить порядок capture/finalize,
late-report policy и bounded deadline: отчёт не должен незаметно переписывать
уже показанный execution outcome.

Для пары проверять минимум old/old, new/old, old/new и new/new:
candidate выключен; candidate включён только в test profile; production profile
включён после receipt. Прогон должен включать новый контракт и прежний сценарий,
lost ACK, duplicate key, разрыв связи, cancellation и неизвестный исход.
Также проверяются несовместимый ID/version/digest и failed contract gate.

Участников может быть больше двух: project coordinator, controller, Windows
worker, project executor, MCP и desktop reader. Фиксируется полный build tuple.
Не обязательно перебирать все комбинации всех версий: поддерживаемый baseline,
каждое разрешённое частичное обновление и новый полный маршрут образуют
конечную документированную матрицу. Случаи вне неё не объявляются совместимыми.

## Совместный gate и включение

Жизненный цикл кандидата:

```text
Proposed → Agreed → Implementing → Verified → PairTested → Enabled
                   consumer/provider       native receipt   scoped policy
```

`Verified` требует прохождения проверок обеих реализаций.
`PairTested` требует совместного прогона кандидатов по согласованным контрактам.
`Enabled` — решение deployment profile, а не следствие загрузки нового binary.
Готовность можно хранить раздельно по сторонам; линейка показывает milestone,
а не обязательный порядок их разработки.

Совместный receipt содержит contract/schema/test pack digests, builds всех
участников, OS/toolchain/environment, проверенные cases, итоги и ссылки
на task/run IDs, outputs и reports. Hash привязывает сведения к артефакту;
в текущей доверенной локальной среде это не новая система аутентификации.

Новые версии запускаются с отдельными instance ID, journal, IPC и тестовым
project workspace. Они не открывают рабочую SQLite параллельно и не подменяют
живые runtime binaries. Test-only профиль разрешает candidate contract,
рабочий профиль продолжает обслуживать v1 до принятия результата.
Отдельный **стабильный путь** validation runtime избегает новой firewall-привязки
для каждого прогона; обновление файлов делается после остановки тестового runtime.

Оркестрация идёт через уже работающий WinBridge worker и обозримый сценарий.
Если появляются тестовые окна, заранее сообщается их назначение;
они явно помечаются как тестовые. Большая часть tests/headless executor должна
проходить автоматически. Ручная проверка остаётся для действительно нового GUI
или поведения, которое автоматизированный сценарий ещё не наблюдает.

## Откат и неизвестные состояния

Выключение v2 для новых запросов не требует возвращать старый binary.
Обновлённый worker продолжает поддерживать v1 и завершает принятые v2 runs.
Это самый дешёвый первый rollback.

Откат binary отдельно требует совместимого journal reader/migrations.
Нельзя обещать, что старый worker прочитает новые persisted enum/schema.
DB restore также не должен терять принятые после backup запросы или приводить
к повторному запуску. Такие условия проверяются отдельным recovery сценарием;
автоматический downgrade и копирование открытой SQLite не подходят.

Старый v1 reader получает только известные v1 состояния и поля.
Новый универсальный read-only обзор может показывать «неподдерживаемое состояние
контракта X/Y» с raw detail и запретом непонятных действий.
Он не должен превращать неизвестный результат в success или выполнять unknown
command. Толерантный reader метаданных и строгий executor команд — разные границы.
