## Порядок работы и результат

1. **Читаемые команды.** Для PowerShell `-EncodedCommand` показывать декодированный
   UTF-16LE сценарий и объяснение, зачем используется кодирование. Точные executable,
   argv и cwd остаются доступными отдельно. Декодирование применяется только к
   отображению уже принятой команды, никогда к повторному исполнению. Неверное
   кодирование имеет видимую причину отказа, а не выдуманный текст сценария.
2. **Долговечное внимание.** Worker хранит события, причину, severity, ссылку на
   задачу и acknowledgement до ответа. Повтор запроса не создаёт второе событие.
   Desktop показывает непрочитанные события, открывает соответствующую задачу и
   подтверждает просмотр отдельным действием. Закрытый UI не теряет события;
   открытие списка не подтверждает их автоматически.
3. **Tray и сигнал.** Закрытие окна после сохранения форм скрывает companion;
   отдельная команда завершает его. Tray count, popup и встроенный звук используют
   тот же журнал внимания. Quiet hours, severity threshold и rate limit управляют
   сигналом, сохраняя событие в журнале. Обычный успешный build по умолчанию тихий;
   ошибка или неизвестный результат требует внимания. Потеря controller не
   переписывает статус выполняющейся задачи.
4. **История и диагностика.** Поиск по проекту/status, keyboard navigation и
   command palette сокращают повседневные действия. Экспорт содержит фактические
   параметры, события и выбранный output; потенциальные секреты редактируются.
   Retention сначала показывает размеры и предлагаемые лимиты: старые пользовательские
   snapshots/reports/history не удаляются автоматически без явной политики.
5. **MCP stdio.** Адаптер вызывает те же controller RPC, что CLI, и возвращает те же
   IDs, ошибки и cursor pages. Он не создаёт собственную очередь исполнения и не
   повторяет команды при неизвестном исходе. Агент получает стандартный вход,
   сохраняя видимость всех действий в Windows UI.

## Проверки и границы

Каждый законченный сценарий проверяется contract/policy tests, настоящим worker и
browser integration. Windows проверки запускаются автоматически через подключённый
worker в отдельных source/state/workspace каталогах; готовые отчёты с checksums
публикуются в `K:\VMs\shared\WinBridge`. Installed exe/config/state и production
Netwatch не заменяются тестовым сценарием. Не назначать повторные мелкие ручные UI
gates: готовые изменения объединяются в обновление runtime.

Первый рабочий срез — читаемый PowerShell и журнал внимания с явным acknowledgement.
Сам по себе этот срез не закрывает весь этап: native tray/popup/sound, настройки,
диагностика и MCP остаются отдельными проверяемыми сценариями выше. Capabilities
объявляются только после реализации; старому worker не отправляются неизвестные RPC.

При архитектурном вопросе или непредвиденном поведении остановиться и уточнить у
пользователя. Проверка отрицательного сценария с заранее ожидаемой ошибкой не является
непредвиденным поведением. Системные настройки, firewall, VMware и безопасность не
меняются в рамках этапа.
